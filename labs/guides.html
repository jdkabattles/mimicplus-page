Guide 1

Prompts that produce a usable OpenAPI spec

A model asked to "write an OpenAPI spec for my users API" will make up fields, status codes, and auth schemes that look right. The fix is to give it evidence, limit what it may invent, and check its output with a tool.

1. Give it examples, not descriptions

Paste real request and response pairs: method, path, query string, relevant headers, body, and status code. Include at least one error response per endpoint if you have one. Remove tokens, cookies, and personal data first. A description like "returns the user" leaves the model to guess the shape. An actual JSON body does not.

2. Pin the version and the rules

Say openapi: 3.1.0 explicitly. Versions 3.0 and 3.1 differ in ways models mix up. For example, 3.1 uses JSON Schema, so a nullable string is type: [string, "null"], while 3.0 used nullable: true. State the conventions you want: an operationId on every operation, shared shapes under components/schemas referenced with $ref, and one error schema used consistently.

3. Make guessing visible

Tell the model to mark anything it inferred rather than observed. A vendor extension such as x-inferred: true is valid OpenAPI (any key starting with x- is allowed), and it lets you search for every guess afterwards. Ask it to list unresolved questions at the end instead of silently choosing.

4. Work one resource at a time

Long specs drift: names change halfway through, and earlier schemas get forgotten. Generate one tag or resource per request, paste the existing components back in each time, and merge the results yourself.

5. Check the output with tools

  • Lint it: npx @redocly/cli lint openapi.yaml, or Spectral with a .spectral.yaml containing extends: ["spectral:oas"] and then npx @stoplight/spectral-cli lint openapi.yaml.
  • Validate your saved example responses against the generated schemas. This is the check that catches invented required fields and wrong types.
  • Read the diff by hand for required lists, enums, and formats such as date-time. These are where models are most confidently wrong.

A prompt you can adapt

You are writing an OpenAPI 3.1.0 document.

Evidence (the only source of truth):
<paste redacted request/response pairs here>

Rules:
- Describe only endpoints, fields, and status codes present in the evidence.
- If a field appears in some responses but not others, make it optional.
- Put reusable shapes in components/schemas and reference them with $ref.
- Give every operation an operationId in camelCase.
- Mark anything you inferred rather than observed with x-inferred: true.
- Do not invent authentication; if a request carried an Authorization
  header, add a securityScheme and note the assumption.

Output: the YAML document, then a list titled "Open questions" with each
assumption you could not confirm from the evidence.
Guide 2

Reviewing breaking changes with an LLM

Do not ask a model to compare two large specs and find what changed. It will miss changes and report some that never happened. Let a diff tool find the changes, then use the model to explain them, judge who is affected, and write the migration note.

1. Get a deterministic diff

oasdiff is an open-source OpenAPI diff tool that compares two specs and reports breaking changes:

git show main:openapi.yaml > base.yaml
oasdiff breaking base.yaml openapi.yaml
oasdiff changelog base.yaml openapi.yaml

In CI, oasdiff breaking base.yaml openapi.yaml --fail-on ERR exits non-zero when it finds an error-level breaking change, so the build fails before the model is involved. The tool stays the gate. The model only helps people understand the result.

2. Know what usually breaks clients

  • Removing or renaming an endpoint, a response field, or an enum value that clients send.
  • Adding a required request field or parameter, or making an optional one required.
  • Narrowing a request type, format, length, or enum that clients already send.
  • Changing a field's type, the meaning of a status code, or the authentication requirements.
  • Adding a new enum value to a response. This is often called non-breaking, but it breaks clients that switch over every value or validate strictly. Flag it for review.

3. Give the model the diff plus context about clients

The diff tells you what changed. Only you know who calls the API. Include whatever you have: which SDKs exist, which endpoints partners use, and whether clients validate responses strictly.

Below is the output of `oasdiff changelog` between the released API and
a proposed change, followed by notes on who calls this API.

<paste diff output>
<paste client notes>

For each change in the diff:
1. Quote the diff line it comes from.
2. Classify it: breaking / breaking for strict clients / safe.
3. Say which known clients are affected and how, or "unknown".
4. Suggest a non-breaking alternative if one exists (e.g. add a new
   field and deprecate the old one instead of renaming).

Do not report any change that is not in the diff. Then draft a short
changelog entry and a migration note for client developers.

4. Check the review

Make sure every item the model reports points to a real diff line, and that every error-level line in the diff appears in the review. If the two don't match, trust the diff. A person decides whether the change ships, whether it needs a version bump, and how long the deprecation period lasts.

Guide 3

A static product page on GitHub Pages for $0

GitHub Pages hosts static files from a repository for free on public repositories. Publishing from a private repository needs a paid GitHub plan. If you use the free <user>.github.io address, the hosting costs nothing. A custom domain costs only its registration fee.

1. Publish

  1. Create a public repository and add index.html at the root.
  2. Add an empty .nojekyll file if you are writing plain HTML. It skips Jekyll processing, so files and folders that start with an underscore are served as-is.
  3. Go to Settings → Pages → Build and deployment, set Source to Deploy from a branch, then choose your branch and the / (root) folder.
  4. Add a 404.html at the root. Pages serves it for missing paths.

Folders become paths: docs/index.html is served at /docs/ and docs/faq.html at /docs/faq.html.

2. Custom domain (optional)

  1. Enter the domain under Settings → Pages → Custom domain. When you deploy from a branch, this commits a CNAME file to the repository.
  2. At your DNS provider, point the apex domain at GitHub's A records 185.199.108.153, 185.199.109.153, 185.199.110.153, and 185.199.111.153. You can also add AAAA records for IPv6. Point www with a CNAME to <user>.github.io.
  3. Verify the domain in your GitHub account's Pages settings. This stops someone else's repository from claiming it if your site is ever unpublished.
  4. Once the certificate is issued, turn on Enforce HTTPS.

3. Security headers without a server

Pages does not let you set response headers, so put a Content-Security-Policy in a <meta http-equiv="Content-Security-Policy"> tag. A policy of default-src 'self' with no inline scripts blocks most injected content. Browsers ignore frame-ancestors when it is set in a meta tag, so that one directive only works as a real header.

4. Taking payment

  • Use a hosted checkout as a plain link, such as a Stripe Payment Link. Stripe's standard pricing has no monthly fee, only per-transaction fees. A plain link needs no third-party script, so your CSP can stay strict.
  • Do not put paid files in the repository. Everything in a public repository and on its Pages site is public, including URLs you never link to. Deliver files through the checkout's post-payment redirect to private storage, or by email.
  • Read GitHub's Pages terms before you sell. GitHub's documentation says Pages is not intended to be a free host for running an online business, an e-commerce site, or a site mainly directed at commercial transactions. Whether a single product page with an outbound checkout link fits within that is your call. Check the current wording.

5. Limits and SEO basics

  • GitHub documents a 1 GB limit on published site size and a soft bandwidth limit of 100 GB per month. Keep video and large downloads elsewhere.
  • Give each page a unique title, a meta description, and an absolute canonical URL. Add sitemap.xml, reference it from robots.txt, and submit it in Google Search Console and Bing Webmaster Tools.
  • Structured data such as Product or SoftwareApplication JSON-LD goes in a <script type="application/ld+json"> block. Browsers don't execute it, so it works alongside a CSP that allows only same-origin scripts.

The Static Product Page Kit ($19) packages these steps as a template. This guide covers everything you need to do it yourself.
