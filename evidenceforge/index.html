How it works: four steps, enforced

EvidenceForge forces agents to follow a contract. Not a suggestion. A contract the validator checks.

  1. 1 · Evidence Registry — A structured map of sources, docs, internal data, and tool outputs. Keys in registry.json map to sources: URLs, files, tool results, internal IDs.
  2. 2 · Strict schema — Outputs in a strict schema where every claim cites evidence IDs. Each record in outputs.jsonl contains claims plus evidence citations plus self-checks.
  3. 3 · Automated validation — The validator fails the build if claims lack support or violate rules. No evidence, no pass. Unknown evidence ID, no pass. Exit code non-zero on failure.
  4. 4 · Machine-readable audit logs — Emit audit logs for human review or compliance systems. Every claim, its evidence, and the check result, in structured JSON.

Built for the Full-Stack Product Architect

The Complete Product Builder

A Full-Stack Developer can build anything. A Product Engineer knows what to build. The Full-Stack Product Architect knows what to build, builds it right, builds it beautiful, and ships it so users pay for it.

That sentence is the anchor. This section earns it: what each builder actually does, where each one fails, and what the hybrid fixes — then what EvidenceForge adds, which is proof.

Build like an engineer, think like a product owner, ship like a founder. EvidenceForge is built for the builder who does all three — and it supplies the one thing neither builder gets for free: proof that every claim the product makes is backed by evidence.

The three builders, compared — honestly

Job titles have no universal definition; the same role can be labelled differently by company, size, and culture. What follows is a working comparison, not a strawman. Each builder is real, each has a failure mode, and the hybrid exists to keep the strengths and kill the failure modes.

Why products fail without evidence

The common thread in product failure is not bad engineering. It is a disconnect between what founders build and what customers will pay for — and that disconnect is measured in conversations and evidence that never happened.

  • Building before validating. Products built on assumptions, not validation. Teams fall in love with an idea and sprint to build before confirming anyone has the problem. Validation is not optional.
  • Overbuilding instead of solving. Launching with dozens of features and complicated dashboards instead of solving one problem really well. More features means more confusion and more delay — and no one knows if anyone needs them.
  • Building in isolation. No feedback loop. Teams guess instead of learning. They listen to what users said — “would you pay for this?” — instead of what users did. Hypothetical answers are hypothetical.
  • Building for scale before proof. Clean architecture for a million users, launched to a handful who barely engage. Over-engineered early products are harder to change, harder to pivot, and create attachment to decisions that need to be killed.
  • Shipping unprovable AI output. A confidently wrong answer in finance, healthcare, legal, or compliance costs trust, deals, and sometimes penalties. “The AI suggested it” is not an answer when a regulator, auditor, or customer asks how a decision was made.

Discovery research gives the antidote a name: evidence, not opinions. Validate an insight against more than one kind of evidence — what people do (behaviour), what people say (attitude), and the context around them — before committing to a build. Run cheap experiments before expensive builds. Treat a discovery stage that never produces a kill decision as a formality, not a gate. A single data point from an actual transaction is worth more than a dozen enthusiastic nods in a stakeholder meeting.

How EvidenceForge fixes the failure mode

EvidenceForge does not replace discovery, design, or engineering judgment. It makes each of them checkable. The validator contract is the mechanism: every claim cites evidence, or the build fails.

  1. Evidence Registry — kills hallucinated requirements. A structured map of sources, docs, internal data, and tool outputs. A requirement, a design decision, or an output claim that cites nothing in the registry is not a decision — it is a guess, and the validator treats it as one.
  2. Strict schema — kills unvalidated features. Outputs in a strict schema where every claim cites evidence IDs. A feature, a number, or a status in the product cannot ship on vibes. If the claim is in the output, its evidence is in the record.
  3. Validation fails the build — the gate that can say no. No evidence, no pass. Unknown evidence ID, no pass. No claims at all, no pass. The build fails with a structured result, so the failure is visible, fixable, and fast — not discovered by a customer after launch.
  4. Machine-readable audit logs — the trail that earns trust. Every claim, its evidence, and the check result, in structured JSON. When a regulator, auditor, or enterprise buyer asks how a decision was made, the answer is a reconstructable trail: prompt, sources, checks, approver, and version — not a summary from memory.

The four phases, with an evidence gate at the end of each

Each phase below ends in a gate. The gate is the same every time: no claim moves forward without evidence.

  1. Phase 1 · Product Discovery & Architecture — Gate: no requirement without evidence. The Architect translates an idea into user flows and information architecture, defines the product data model — the core entities and their relationships — and chooses the right stack for the product, not just what is trendy. EvidenceForge gate: the data model and every requirement are evidence-backed. Every entity, every claim, every flow cites its source. A requirement with no evidence does not enter the build.
  2. Phase 2 · Frontend, Product-Grade UI — Gate: no UI claim without evidence. Pixel-perfect, state-aware UI that handles the edge cases other builders ignore: loading skeletons, optimistic updates, empty states, error boundaries, undo actions, keyboard shortcuts. EvidenceForge gate: EvidenceForge validates the claims the UI shows. Every number, every status, every result in the UI must cite evidence — or the build fails. Optimistic UI still shows a state, but the state it shows is a checked claim, not an invented one.
  3. Phase 3 · Backend, Engineer-Grade — Gate: no API claim without evidence. A typed, self-documenting API. Full auth from day one. The hard stuff: subscriptions and webhooks, roles and permissions, file processing, email queues, real-time. A database designed for growth: proper indexing, migrations, soft deletes, audit logs. EvidenceForge gate: EvidenceForge validates API outputs. Every claim the API returns cites evidence. Audit logs are machine-readable, and subscriptions, roles, and file processing are all auditable — the same trail an auditor will ask for later.
  4. Phase 4 · Ship, Measure, and Scale — Gate: every iteration re-proven. One-command deploy with CI/CD, preview deployments, monitoring. Ship an MVP fast, measure where users drop off, re-engineer the weak point with scalable code, repeat. EvidenceForge gate: EvidenceForge is the Iteration Engine's truth layer. Ship the MVP fast, measure drop-off, re-engineer the weak point — and EvidenceForge proves each iteration is still backed by evidence. Speed does not erode proof; each iteration re-passes the same gate.

Why proof is what makes users pay

Customers do not pay for elegance. They pay to make pain go away — lost money, wasted hours, compliance exposure, operational chaos, missed revenue. Those are urgent problems, and urgency is what makes someone pull out a card. But urgency alone does not close an enterprise deal, and it does not survive an audit.

What closes the deal is trust, and trust in regulated work is not a feeling — it is evidence. High-risk AI systems are expected to generate logs that let a reviewer trace what happened: the period of use, the sources checked, the input that led to a given output, and who verified the result. Compliance work is largely an evidence-collection exercise: logs, records, and proof that controls operated. A vendor survey of enterprises running AI agents in production reported that most could not fully audit how those systems operated — a gap that becomes compliance debt, security exposure, and lost deals. EvidenceForge is built to close exactly that gap at the claim level, before it becomes an audit failure.

The final deliverable, then, is not just a website. Not just a pretty app. A Revenue-Ready Digital Product — a complete SaaS, marketplace, or platform that looks designed with care, works reliably, and scales — and proves every claim with evidence, so the buyer, the auditor, and the regulator can all check it.

The Architect knows what to build, builds it right, builds it beautiful, and ships it so users pay for it. EvidenceForge proves it, claim by claim, with evidence.

Try it: tap a claim, see its evidence

The first claim below is the real example from the repo (checks/outputs.example.jsonl). The other two are illustrative cases built from the validator rules in evidenceforge/cli.py — they show exactly what fails and why. Nothing here is live-streaming. You drive it.

Claim c1 — PASS

Evidence: system-prompt:guidelines

Resolves to: https://docs.x.ai/grok/overview (from the repo registry).

Self-check: all_claims_have_evidence: true · missing_evidence_for: [] · rule_violations: [].

Source: checks/outputs.example.jsonl + .evidenceforge/registry.json in the repo.

Validator rules, from validate_record in cli.py: a claim with no evidence is listed in missing_evidence_for; an evidence ID not in the registry is a unknown_evidence:<id> violation; a record with no claims is a no_claims violation. Any violation means status fail.

The registry: real keys from the repo

Seven keys ship in .evidenceforge/registry.json. Every claim on this site cites one of them, or it fails.

  • system-prompt:tools — https://docs.x.ai/developers/tools/overview
  • system-prompt:models — https://docs.x.ai/developers/models
  • system-prompt:guidelines — https://docs.x.ai/grok/overview
  • acceptable-use — https://x.ai/legal/acceptable-use-policy
  • model-card:grok-4 — https://data.x.ai/2026-04-07-grok-4-20-model-card.pdf
  • internal-eval:2026-10 — internal-eval:2026-10
  • example-domain:legal-contract — domains/legal/contract-rules.json

The registry is the source of truth for what counts as evidence. If an ID is not in the registry, the validator reports it as unknown evidence and the record fails.

Quick start

From the README. Three commands, then you write your agent.

pip install evidenceforge
evidenceforge init
# edit .evidenceforge/registry.json and write your agent
evidenceforge validate outputs.jsonl

Validation reads outputs.jsonl against .evidenceforge/registry.json, prints a structured JSON summary (status, records_checked, per-record results), and exits non-zero on failure. Missing outputs or registry files fail with outputs_not_found / registry_not_found.

Output schema (from .evidenceforge/instructions.md)

{
  "status": "ok" | "fail",
  "timestamp": "ISO-8601",
  "claims": [
    { "id": "claim-1", "text": "The claim text",
      "evidence": ["registry-key-1", "registry-key-2"] }
  ],
  "self_check": {
    "all_claims_have_evidence": true,
    "missing_evidence_for": [],
    "rule_violations": []
  }
}

Agent instructions ship as .evidenceforge/instructions.md — drop-in contract so Grok, Claude, or any coding agent knows it. Read order: instructions, then registry, then any domain packs in .evidenceforge/domains/.
