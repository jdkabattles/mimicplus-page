Governed multi-agent engine · $0 · MIT

An agent that cannot outrun its own rules.

Governed Agent Engine is a small, governed multi-agent engine that installs on an Android phone (Termux) with one command and runs at $0. The core is Python stdlib plus PyYAML: no Rust, no compiler.

Most agent frameworks ask the model to behave. This one does not take the model's word for it. Every plan is checked before it reaches the backlog. Every done needs evidence. Governance changes halt the agent. The rules are not suggestions — they are enforced, in code, before anything runs.

inbox → normalize → validate (governance) → route → execute or plan → backlog → replay → evidence

How it works: the loop

One gae run --once cycle. Each step is enforced; a failure stops the cycle instead of sliding past it.

  1. 1 · Governance integrity. The governance.yaml fingerprint must equal the one loaded at start. A change while running halts the agent.
  2. 2 · Intake. Every artifacts/inbox/*.json file, sorted, is parsed.
  3. 3 · Normalize. {"task": {...}} envelopes are unwrapped; type / action are trimmed and lower-cased.
  4. 4 · Validate — APCK governance, deny by default. Strict task parsing, then the APCK check: task type, action allowlist, recursion depth, input size, governance mutation (always refused), human-approval flag. Rejected files move to inbox/rejected/.
  5. 5 · Route — pure function. Tasks that require Grok go to Grok, always. Cognition-only types go to cognition. Grok AVAILABLE goes to Grok; otherwise cognition with the per-type chain.
  6. 6 · Execute or plan. Grok: a BacklogEntry is written — the handoff. Cognition: a strategy produces a Plan (advisory only) written to artifacts/plans/.
  7. 7 · Backlog. Immutable entry. Human-gated actions start in awaiting_approval.
  8. 8 · Replay on AVAILABLE. The heartbeat is re-probed; if Grok is (or just became) AVAILABLE, evidence is reconciled and outstanding Grok entries are re-dispatched in (created_at, priority, entry_id) order.
  9. 9 · Evidence. GrokResult files + heartbeat.json, written by the executor. A done without the required evidence is reconciled as FAILED.

Determinism where it counts: injected clocks, hash-derived entry ids, a pure router, sorted inbox and backlog iteration, temperature: 0. LLM text stays non-deterministic and is confined to Plan.raw_text.

Governance: APCK — Artifacts, Process, Constraints, Knowledge

Defined in config/governance.yaml, typed as GovernanceConfig, enforced by the orchestrator. Loaded once, fingerprinted; any change while running halts the agent.

APCK pillars and the rules each enforces.
PillarEnforced rules
A · ArtifactsWrites only under write_roots (default artifacts/). done requires an evidence file.
P · ProcessFixed lifecycle. allowed_task_types. Human-approval actions only enter the backlog as awaiting_approval and only with human_approval: true. Top-level tasks need a human issuer (see identities).
C · ConstraintsDeny-by-default allowed_actions. max_recursion_depth (sub-tasks must name parent_task_id). max_inputs_bytes. cost_ceiling_usd must be 0.0. governance_mutable must be false.
K · KnowledgeOnly allowed_endpoints may be consulted. sensitive tasks never go to third_party_proxy / community endpoints unless explicitly allowed. Cognition output is advisory only.

Hard-coded, not configurable

  • Human-approval actions: send_message, delete, purchase, publish, trade, modify_governance. Config can add to this set, never remove from it. No flag disables it.
  • modify_governance is refused even with human_approval: true. Governance changes happen only by a human editing config/governance.yaml in a reviewed commit and restarting.
  • A running agent re-fingerprints governance.yaml before every cycle and every submit — and halts if it changed.
  • cost_usd on every endpoint and cost_ceiling_usd must be exactly 0.0, or config will not load. $0 is enforced, not aspirational.

Approving a gated entry

Change only status from awaiting_approval to approved in the backlog JSON (append a status_history item), commit, push. The executor picks it up on its next run.

The doctrine gate: every plan is checked

Example doctrine: do the work completely, ground every claim in evidence, analyse every failure, and improve after each run. That statement is pinned in code and in config — the loader rejects any rewording, and the running agent stops if the file changes.

A PlanStep is index, description, kind (gather | analyze | execute | verify | improve), evidence_required, failure_modes. Cognition models are asked for this JSON shape, and their system prompt starts with the doctrine statement. Plans in the old numbered-text format still parse, but their steps have no kind — so the gate rejects them.

  1. Minimum steps and length. A lazy-plan floor (min_steps, min_step_chars). Duplicate steps are also rejected.
  2. Typed step kinds. Execute / verify steps must set evidence_required; a verify step must exist.
  3. Failure modes. Execute steps must list failure_modes; every rejection is written as evidence.
  4. Improve after verify. A kind: improve step must come after a kind: verify step.
  5. Truth first. truth_priority: 1 is the only accepted value — truth outranks speed, brevity, and convenience.

Enforcement flow: the planner asks the best-ranked model; the gate checks the parsed plan — for every plan, whichever model wrote it, before the backlog. If the plan breaks the doctrine, the orchestrator writes a rejection as evidence (violations, model, the full plan, doctrine fingerprint), the model gets the laziness penalty and is excluded, and the next model in the fallback chain is asked (up to 4 models). If every model fails, DoctrineError is raised, nothing enters the backlog, the CLI exits with code 5, and inbox files move to rejected/.

Tap a plan to see the gate's verdict. The cases below are illustrative plans built from the gate rules in docs/doctrine.md — they show exactly what fails and why. Nothing here is live engine output. You drive it.

Plan A — PASS

PASS

Result: Passes the doctrine gate. Enters the backlog.

Steps: gather (evidence_required) → analyze → execute (evidence_required, failure_modes) → verify (evidence_required) → improve (after verify).

Rule fired: None. Typed kinds, evidence flags, failure modes, and improve-after-verify all present.

The four outcomes, without JS: A passes and enters the backlog. B is rejected (no improve step) — model penalized, next model tried. C is rejected — the word “improve” in the text does not count. D passed the gate but reported done without evidence — reconciled as FAILED, agent penalized.

Why kind == "improve" and not substring matching: a check like "improve" in description passes for “verify, then improve nothing”. Any model learns to sprinkle the word in, so the check says nothing about whether the plan improves anything. A typed kind, placed after a verify step, is a structural claim the gate can check — and a test proves that adding the word “improve” to the text does not pass.

Identities & authority: code, not config

One file per principal in identities/, restated for humans and other tools — but the code is the source of truth. A YAML edit cannot mint a new high-authority principal. A non-human identity is not allowed to hold authority ≥ 50.

Principals: type and authority. Only humans hold authority ≥ 50, except the Overseer at exactly 50.

  • Top-level tasks need a human issuer with authority ≥ min_top_level_authority (default 100, bounded 50–100, so config can never let an executor or cognition model start work). The Overseer may issue them only if governance sets overseer_may_issue_top_level: true — and can never approve human-approval actions.
  • Child tasks can be issued by any known identity, within max_recursion_depth. The provenance chain must end at parent_task_id, match the parent's recorded chain in the backlog, and lead back to a root issued by sufficient human authority.
  • gae submit stamps issued_by: owner when the task names no issuer: the person at the terminal is the human. Inbox files get no default — a file without a valid human issued_by is rejected for top-level work.

Agent selection & routing penalty: lazy is expensive

Two penalties, no double counting. A plan rejected by the doctrine gate never reaches the backlog, so it can never also produce an agent routing record. Each failure is penalised once, at the layer that caused it.

Per-model penalty vs agent-level routing penalty.
Per-cognition-model penaltyAgent-level routing penalty
WhoA free model endpointGrok, Acquirer, Analyst
WhenA model's plan fails the doctrine gate, before the backlogA reconciled run lacks required artifacts / evidence
Valuelaziness_penalty (0.5) on that model's fallback scoreThe agent's LAZINESS_PENALTY from .grok
EffectDemotes the model in the cognition fallback chainRouting record in the hash-chained ledger
  • Selection window: the last N = 10 completed runs of the agent. routing_score = penalty ** lazy_in_window. With the shared penalty high = 0.5: 1 lazy → 0.5 eligible; 2 lazy → 0.25 blocked (threshold 0.50). Honest failure (the executor reports failed) is not lazy and writes no run record. Lazy means the run claimed done without the required artifacts or evidence.
  • Blocks are sticky. After a block, lazy runs ageing out of the window do not unblock. Only an Owner-signed record in migrations/unblocks/*.grok unblocks. The Overseer is never selectable.
  • Held, not dropped. A task whose agent is blocked is created in the backlog with status blocked_agent and is never dispatched. Each replay re-selects held entries; once the agent is eligible the entry moves to pending (or awaiting_approval).
  • Hash-chained ledgers under artifacts/evidence/routing/: routing records, selection records, block records. Editing, deleting, or reordering a line breaks the chain. Tamper-evident, not tamper-proof — the ledger is also committed with the artifacts.
  • Every block writes a block report — WHO, WHAT, WHERE, WHEN, HOW, WHY — hash-linked into the chain. The audit marks it NON_COMPLIANT when a block has no report, a report is missing or altered, or a report does not describe that block.

The .grok spec: a constitution the code can check

.grok is a strict subset of YAML 1.2 that any language can parse. Native code is primary and executable; the .grok files are the read-only constitutional mirror and audit source of truth.

  • Startup binds them and fails fast with a named error code — IDENTITY_MISMATCH, DOCTRINE_MISMATCH, DIRECTIVE_MISMATCH, GOVERNANCE_MISMATCH, COGNITION_MISMATCH, ACQUISITION_MISMATCH, CLARIFICATION_RULE_MISSING, NON_COMPLIANT. The runtime exposes one AgentIdentity per agent — always the native object.
  • Drift detection: the orchestrator re-computes the charter fingerprint before submit, replay, approve, block, and every run cycle. A change halts with UNAUTHORIZED_GROK_CHANGE unless migrations/ contains a matching Owner-signed migration record.
  • Every enforced native rule is derivable from doctrine.grok. The laziness-penalty thresholds (low 0.9 / medium 0.75 / high 0.5 / maximum 0.25) were approved by Owner on 2026-10-11.
  • Overseer audit: gae audit runs every check without stopping at the first, writes artifacts/evidence/audits/audit-<UTC>.json, and exits 0 when compliant, 6 otherwise.

Free cognition: seven adapters, advisory only

Pollinations, LLM7, OVH, AI Horde, OpenRouter free, Gemini, and Groq. Health tracking and rate limits, plus cross-checks: JSON repair, code verification, honesty audit, majority vote.

  • Cognition plans; it never executes. Strategy selects endpoints by type affinity, enabled state, K-policy, health, and token buckets. cognition_is_advisory: true.
  • Optional free keys come from the environment only: OPENROUTER_API_KEY, GEMINI_API_KEY, GROQ_API_KEY. Never hard-coded, never committed. gae smoke is a live ping of enabled endpoints — opt-in, uses network.
  • gae bench --write-capabilities measures your providers and writes config/capabilities.yaml. Until you run it, capability scores stay neutral at 0.5.

Executor transport: a git / file queue

Backlog out, evidence and heartbeat back. It works with any executor that can read and write files, such as a scheduled Grok Bot routine.

  1. git pull.
  2. For each backlog entry with status pending or approved, sorted by (created_at, priority, entry_id): validate against the backlog-entry schema, do the work under the executor's own governance, write artifacts/evidence/<entry_id>.json.
  3. Never execute awaiting_approval, rejected, done, or failed entries.
  4. Write artifacts/evidence/heartbeat.json.
  5. Commit + push evidence only.

Evidence of truth: when a backlog entry has a plan, the result's outputs.evidence must map each evidence_required step index (as a string) to a non-empty file under artifacts/. A done result without it is reconciled as FAILED.

Get started

Termux (Android)

curl -fsSL https://raw.githubusercontent.com/jdkabattles/governed-agent-engine/main/termux/install.sh | bash

Or clone and run the installer. It runs pkg install python git (prebuilt packages only), creates a venv, runs pip install -e ., puts a gae launcher on PATH, and validates the config. Overrides: GAE_DIR, GAE_REPO_URL, GAE_BRANCH, GAE_RUN_ONCE=1.

Linux / macOS

git clone https://github.com/jdkabattles/governed-agent-engine && cd governed-agent-engine
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"

Use

gae validate                     # load + validate all config
gae status                       # executor state in plain words, backlog counts, blocks
gae example --out task.json      # write a valid example task (--type research|market_watch|...)
gae submit examples/task.json    # or --json '{...}' or stdin
gae run --once                   # one cycle
gae audit                        # overseer audit -> artifacts/evidence/audits/
gae blocks                       # agent blocks, scores, held tasks
gae smoke                        # LIVE ping of enabled endpoints (opt-in, uses network)
gae bench --write-capabilities   # LIVE capability benchmark -> config/capabilities.yaml

Bad input prints one line (gae: error: ...) and exits non-zero. GAE_DEBUG=1 shows a traceback.

Make it yours

  1. Doctrine: set your statement in core/doctrine.py DOCTRINE_STATEMENT, config/doctrine.yaml, doctrine/doctrine.yaml, config/doctrine.grok, and every config/agents/*.grok. The binding keeps all copies identical (startup fails otherwise).
  2. Agents: identities are fixed in core/identity.py and restated in identities/*.yaml, config/identity.grok, and config/agents/*.grok. Edit all of them together.
  3. Directives: replace DIRECTIVE / RESPONSE_WINDOW in config/directive.grok and the agent packages.
  4. Capabilities: gae bench --write-capabilities measures your providers.
  5. After the first deployment, record every change to these files as an owner-signed migrations/*.grok record (drift protection).

Using the engine from a private deployment

Keep your own doctrine, agents, and history in a private repo and consume this engine as a dependency. --root (or GAE_ROOT) points the engine at a directory holding your config/, identities/, doctrine/, migrations/, and artifacts/. The doctrine statement and identity table stay pinned in code — a private deployment that changes them carries a small overlay of those two modules until they become configurable.

pip install "governed-agent-engine @ git+https://github.com/jdkabattles/governed-agent-engine@v0.1.0"
gae --root /path/to/private-config-repo status

Built for the Full-Stack Product Architect

The Complete Product Builder

A Full-Stack Developer can build anything. A Product Engineer knows what to build. The Full-Stack Product Architect knows what to build, builds it right, builds it beautiful, and ships it so users pay for it.

That sentence is the anchor. This section earns it: what each builder actually does, where each one fails, and what the hybrid fixes — then what Governed Agent Engine adds, which is proof enforced by gates, not promised by vibes.

Build like an engineer, think like a product owner, ship like a founder. Governed Agent Engine is built for the builder who does all three — and it supplies the one thing neither builder gets for free: an agent that cannot ship an unproven claim, because the gate says no before the backlog says yes.

The three builders, compared — honestly

Job titles have no universal definition; the same role can be labelled differently by company, size, and culture. What follows is a working comparison, not a strawman. Each builder is real, each has a failure mode, and the hybrid exists to keep the strengths and kill the failure modes.

Three builders: what each answers, what each is strong at, where each fails, and what Governed Agent Engine adds.

On titles: a full-stack developer builds across the stack and ships features; a full-stack engineer carries added responsibility for how the product holds up as it scales — one asks “does this work?”, the other asks “does this work, and will it keep working?” Product-minded engineers want to understand why decisions are made and how people use the product. The hybrid in this section combines all three questions.

Why products fail without governance

The common thread in product failure is not bad engineering. It is a disconnect between what founders build and what customers will pay for — and that disconnect is measured in conversations and evidence that never happened.

  • Building before validating. Products built on assumptions, not validation. Teams fall in love with an idea and sprint to build before confirming anyone has the problem. Validation is not optional.
  • Overbuilding instead of solving. Launching with dozens of features and complicated dashboards instead of solving one problem really well. More features means more confusion and more delay — and no one knows if anyone needs them.
  • Building in isolation. No feedback loop. Teams guess instead of learning. They listen to what users said — “would you pay for this?” — instead of what users did. Hypothetical answers are hypothetical.
  • Building for scale before proof. Clean architecture for a million users, launched to a handful who barely engage. Over-engineered early products are harder to change, harder to pivot, and create attachment to decisions that need to be killed.
  • Shipping unprovable AI output. A confidently wrong answer in finance, healthcare, legal, or compliance costs trust, deals, and sometimes penalties. “The AI suggested it” is not an answer when a regulator, auditor, or customer asks how a decision was made.

Discovery research gives the antidote a name: evidence, not opinions. Validate an insight against more than one kind of evidence — what people do (behaviour), what people say (attitude), and the context around them — before committing to a build. Run cheap experiments before expensive builds. Treat a discovery stage that never produces a kill decision as a formality, not a gate. A single data point from an actual transaction is worth more than a dozen enthusiastic nods in a stakeholder meeting.

How Governed Agent Engine fixes the failure mode

Governed Agent Engine does not replace discovery, design, or engineering judgment. It makes each of them checkable. The doctrine gate and APCK governance are the mechanism: every plan is checked, every done needs evidence, or the run fails.

  1. Doctrine gate — kills lazy plans. Typed step kinds, evidence flags, failure modes, and improve-after-verify. A plan that cannot say how it will prove its work never reaches the backlog. The substring trick does not pass.
  2. APCK governance — kills ungoverned actions. Deny-by-default actions, hard-coded human-approval actions, a fingerprint that halts the agent on change, and a $0 cost ceiling that config cannot loosen. The agent cannot talk itself past its own rules.
  3. Evidence of truth — kills “done” without proof. A done result without the required evidence is reconciled as FAILED, with an evidence_check.json recording why. The failure is visible, fixable, and fast — not discovered by a customer after launch.
  4. Hash-chained ledgers + block reports — the trail that earns trust. Routing, selection, and block records, hash-linked. Every block writes a WHO / WHAT / WHERE / WHEN / HOW / WHY report. When an auditor or buyer asks how a decision was made, the answer is a reconstructable trail — not a summary from memory.

The four phases, with a governance gate at the end of each

Each phase below ends in a gate. The gate is the same every time: no plan moves forward without passing the doctrine check, and no done counts without evidence.

  1. Phase 1 · Product Discovery & Architecture — Gate: no requirement without evidence. The Architect translates an idea into user flows and information architecture, defines the product data model — the core entities and their relationships — and chooses the right stack for the product, not just what is trendy. Governed Agent Engine gate: the doctrine statement and governance fingerprint are pinned before anything runs. A plan for discovery work must carry typed steps, evidence flags, and failure modes — a requirement with no evidence path does not enter the backlog.
  2. Phase 2 · Frontend, Product-Grade UI — Gate: no UI claim without evidence. Pixel-perfect, state-aware UI that handles the edge cases other builders ignore: loading skeletons, optimistic updates, empty states, error boundaries, undo actions, keyboard shortcuts. Governed Agent Engine gate: the agent's plan for UI work is gate-checked the same way, and any done it reports must cite its evidence — screenshots, checks, or artifacts under artifacts/. Optimistic UI still shows a state, but the state it shows is a checked claim, not an invented one.
  3. Phase 3 · Backend, Engineer-Grade — Gate: no API claim without evidence. A typed, self-documenting API. Full auth from day one. The hard stuff: subscriptions and webhooks, roles and permissions, file processing, email queues, real-time. A database designed for growth: proper indexing, migrations, soft deletes, audit logs. Governed Agent Engine gate: backend work goes through the same gate, and the human-approval set means the agent can never send, delete, purchase, publish, trade, or change governance on its own. Sensitive tasks never go to third-party or community endpoints unless explicitly allowed.
  4. Phase 4 · Ship, Measure, and Scale — Gate: every iteration re-proven. One-command deploy with CI/CD, preview deployments, monitoring. Ship an MVP fast, measure where users drop off, re-engineer the weak point with scalable code, repeat. Governed Agent Engine gate: Governed Agent Engine is the Iteration Engine's truth layer. Ship the MVP fast, measure drop-off, re-engineer the weak point — and the gate re-proves each iteration. Speed does not erode proof; each iteration re-passes the same gate, and lazy agents get penalised out of the rotation.

Why proof is what makes users pay

Customers do not pay for elegance. They pay to make pain go away — lost money, wasted hours, compliance exposure, operational chaos, missed revenue. Those are urgent problems, and urgency is what makes someone pull out a card. But urgency alone does not close an enterprise deal, and it does not survive an audit.

What closes the deal is trust, and trust in regulated work is not a feeling — it is evidence. High-risk AI systems are expected to generate logs that let a reviewer trace what happened: the period of use, the sources checked, the input that led to a given output, and who verified the result. Compliance work is largely an evidence-collection exercise: logs, records, and proof that controls operated. A vendor survey of enterprises running AI agents in production reported that most could not fully audit how those systems operated — a gap that becomes compliance debt, security exposure, and lost deals. Governed Agent Engine is built to close exactly that gap at the run level, before it becomes an audit failure: hash-chained ledgers, block reports, and evidence for every done.

The final deliverable, then, is not just a website. Not just a pretty app. A Revenue-Ready Digital Product — a complete SaaS, marketplace, or platform that looks designed with care, works reliably, and scales — and proves every claim with evidence, so the buyer, the auditor, and the regulator can all check it.

The Architect knows what to build, builds it right, builds it beautiful, and ships it so users pay for it. Governed Agent Engine proves it, plan by plan, with evidence.
